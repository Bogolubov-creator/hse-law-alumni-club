# Подготовка анализа защищённости через ЕЛК

После выделения ресурсов и настройки целевого окружения владелец подаёт заявку
через ЕЛК. До подачи собирается состав работающей установки и результаты проверок
того же выпуска. Состав checkout, успешная сборка и отсутствие находок сканера
сами по себе не подтверждают защищённость сервера.

## Состав и границы проверки

| Область | Что фиксировать и проверять |
|---|---|
| Python и приложения | Полные версии Python, Django, Gunicorn, Django Ninja, Jinja2, Pydantic и pydantic-core; остальные прямые и транзитивные зависимости API, web и оператора |
| Системные библиотеки | Пакеты итоговых образов, включая OpenSSL, PCRE2, expat, Connector/C и libc; пакеты и ядро целевой Ubuntu |
| Периметр | nginx или Caddy выбранного контура, подключённые модули, фактическая конфигурация TLS, HTTP, заголовков и лимитов |
| База данных | Версия работающей MariaDB или PostgreSQL, версия пакета с суффиксом дистрибутива, права прикладной роли, доступность порта и восстановление копии |
| Идентичность выпуска | SHA checkout, изменения файлов, label каждого контейнера, image ID и доступные registry digest; соответствие отчётов этому выпуску |
| Поддержка | Поддерживаемые ветки и сроки поддержки у поставщика; доступность официальных исправлений для используемой платформы |
| Применимость CVE | Точный пакет и диапазон версий, необходимые модули и настройки, достижимость через используемый протокол, влияние на приложение |

Рабочий web использует Django/Jinja2 и собственные браузерные модули. Vue и
`@vue/server-renderer` в этом checkout не используются. Строку из внешнего примера
нельзя переносить в состав приложения. Если компонент появится, проверяют конкретный
пакет, режим рендеринга и полный граф его зависимостей.

APT-версии учитываются целиком: Ubuntu может переносить исправление в пакет без
смены основной upstream-версии. Применимость сверяется с
[Ubuntu Security](https://ubuntu.com/security/cves), а не только сравнением цифр.
После обновления пакета проверяют перезапуск сервиса; установленный новый пакет
не доказывает, что работающий процесс уже использует его.

## Уточнения к письму от службы безопасности

Сведения ниже сверены 5 октября 2026 года. Перед выпуском источники проверяют снова.

| Компонент | Факт и решение |
|---|---|
| Django | CVE-2025-64459 исправлена в 5.2.8 для ветки 5.2; SQL-инъекция связана с передачей `_connector` через раскрытие словаря. В проекте закреплена 6.1.1. Для каждой ветки используют её бюллетени; номер 5.2.17 нельзя применять к 6.1 как универсальный порог |
| nginx | CVE-2026-42533 исправлена в 1.30.4, а CVE-2026-90439 – в 1.30.5. Образ закреплён на 1.30.5 и digest. Проверяют фактический образ, PCRE2 и модули; отсутствие проблем с одной CVE не является заключением по всему nginx |
| Gunicorn | 26.2.0 опубликована в PyPI. Сайт релизов показывает 26.2.1/26.2.2, но официальный API PyPI и повторное разрешение зависимостей их не предоставили. Сохранена устанавливаемая 26.2.0; доступность исправлений после неё и применимость заявленных ошибок ASGI остаются открытым вопросом перед выпуском. Настройки запуска в коде: HTTP/1, h2c выключен, keepalive 0, доверенные forwarded IP отсутствуют, PROXY protocol выключен. Это сужает условия некоторых ошибок, но не закрывает все ошибки ASGI. Переход на 23.x без основания не выполняется |
| Pydantic | В lockfile закреплены 2.13.5 и совместимый pydantic-core 2.46.5. CVE-2024-3772 исправлена уже в 2.4.0 для ветки 2.x. Требование более новой версии связывают с отдельной CVE либо конкретным исправлением |
| Оценка риска | CVSS записывается с версией шкалы, автором оценки и вектором. Например, для CVE-2026-42533 у F5 указаны 9.2 по CVSS 4.0 и 8.1 по CVSS 3.1. Это нельзя смешивать в одной колонке без пояснения |

## Воспроизводимые отчёты

Из checkout выбранного выпуска с синхронизированными Python-окружениями:

```bash
bash scripts/checks/audit-dependencies.sh security-reports
```

Каталог должен быть новым. Команда сохраняет `source.json` с составом трёх lockfile,
прямыми зависимостями, стадиями Docker-сборки и хешами файлов, а также шесть отчётов
pip-audit: runtime и development для backend, frontend и scripts. Проверяются все
области даже при находке в одной из них. Ненулевой код означает находку либо сбой;
отсутствующий отчёт не считается успешной проверкой. Требования с hash экспортируются
из frozen lockfile; resolver не обновляет версии незаметно.

CI сохраняет отчёты Python и итоговых образов как артефакты с SHA в имени на семь
дней. Trivy сохраняет находки всех уровней. HIGH, CRITICAL и неизвестная критичность
останавливают задание; MEDIUM и LOW остаются видимыми для разбора. Новая находка
не скрывается исключением ради успешного CI. Из отчётов образов удаляется конфигурация,
включая env и историю сборки. Проверки образов относятся к собранным в CI образам,
а не автоматически к контейнерам на сервере.

На целевой Ubuntu для нового MariaDB/nginx-контура, из `/opt/club`:

```bash
sudo install -d -m 0700 /root/club-security-assessment
sudo python3 scripts/diagnostics/security-inventory.py \
  --output /root/club-security-assessment/runtime.json \
  --host \
  --container api="$(sudo docker compose --env-file /etc/club/compose.env -f deploy/compose.mariadb.yml ps -q api)" \
  --container web="$(sudo docker compose --env-file /etc/club/compose.env -f deploy/compose.mariadb.yml ps -q web)" \
  --container nginx="$(sudo docker compose --env-file /etc/club/compose.env -f deploy/compose.mariadb.yml ps -q nginx)"
sudo sh -c 'umask 077; mariadb --batch --skip-column-names --execute "SELECT VERSION();" > /root/club-security-assessment/mariadb-server.txt'
```

`runtime.json` должен быть новым файлом. Скрипт требует Python 3.12+, не устанавливает
пакеты и не читает env, журналы, пользовательские данные или TLS-ключи. Собирает версии
и пакеты только указанных работающих контейнеров, image ID, label и registry digest,
а с `--host` – пакеты Ubuntu и ядро. Остановленный или недоступный контейнер даёт
частичный отчёт и ненулевой код. `assessment_performed=false` остаётся даже при полном
сборе состава: инвентаризация не выдает заключение о защищённости.

Отдельно сверяют пакеты контейнеров с lockfile и image ID с очищенными отчётами Trivy.
API и web должны соответствовать выбранному выпуску; метки разных SHA, отсутствующий
digest или несовпадение состава требуют разбора. Для прежнего контура используют
параметры его Compose и роли `caddy`/`postgres`. На Docker-хосте сохраняют также вывод
`docker version` и `docker compose version`, а версию работающей PostgreSQL запрашивают
через `SELECT version()` в уже разрешённом локальном сеансе. Не подставляют секреты в
аргументы или отчёт. Пакеты остановленного оператора проверяются по скану его образа.

## Проверка конфигурации и подготовка заявки

Перед подачей заявки проверяют на том же выпуске:

1. Извне доступны только согласованные входные порты; API и база закрыты.
2. TLS, редиректы, CSP, ограничения заголовков и тела, таймауты, rate limit и
   передача клиентского IP работают в выбранном nginx/Caddy-контуре.
3. Неверные и неоднозначные HTTP-запросы не обходят периметр. Проверены сочетания
   Content-Length/Transfer-Encoding, повторные заголовки и используемый worker Gunicorn.
4. Роли, SQL-параметры, экранирование шаблонов, загрузки и обращения к внешним
   сервисам проверены профильными тестами. Нет передачи пользовательского словаря
   напрямую в параметры ORM. Для ReDoS учитываются реальные входы и лимиты данных.
5. Сервисы после обновления перезапущены; восстановление копии и откат проверены
   в изолированной среде. Работающая база не заменяется автоматически.

В заявку включают согласованный адрес и контур, ответственного, точные версии,
SHA и image ID/digest, даты сканирования, очищенные отчёты и открытые вопросы.
Учётные записи для анализа, временные доступы и окно тестирования согласуются
отдельно. Закрытые файлы конфигурации, данные участников и секреты не прикладывают.

Для каждой находки ведут строку: пакет и фактическая версия; CVE/GHSA; источник и
дата; CVSS; диапазон; условия и доказательство применимости; исправление;
повторная проверка; остаточный риск и решение ответственного. Допустимые выводы:
«исправлена указанная CVE», «условия не выполняются, проверено», «требует проверки».
Формулировка «всё чисто» не заменяет анализ. Принятие остаточного риска выполняет
ответственный владелец совместно со службой безопасности.

Порядок обновления, резервирования и отката – в
[runbook](deploy-runbook.md) и [инструкции MariaDB](mariadb-migration.md).
