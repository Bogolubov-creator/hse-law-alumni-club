# Заявки: изменение данных и откат

08.09.2026. Только отдельная база alumni_staged. Миграция apps/api/migrations/20260908-checkout.sql выполнена на ней. Повторный запуск безопасен (CREATE TABLE IF NOT EXISTS); схема исходных коллекций не изменяется.

Новый контур использует CHECKOUT_DATABASE_URL, PostgreSQL того же Directus. Нужен pg в API. Обход небезопасного контура при отсутствии подключения не предусмотрен: операции возвращают ошибку, production-конфигурация требует эту переменную. В production ничего не выполнялось.

Резерв мерча возникает при сохранении заявки. В одной транзакции блокируются корзина, строки каталога, сверяются актуальные цена/вариант/статус/скидка, уменьшается доступный остаток, создаётся заявка и очищается корзина. Неуспешная операция откатывается полностью. Обычные изменения корзины используют тот же ключ блокировки. Это изменение складской логики: прежний код только проверял остаток и никогда его не уменьшал.

Ключ Idempotency-Key хранится клиентом до подтверждённого ответа; сервер хранит только его SHA-256 вместе с хешем тела и владельца, UUID заявки и квитанцией. Повтор возвращает исходный результат. Смена тела с тем же ключом отклоняется. В квитанции нет контактных ПДн. Запись переживает перезапуск API.

Отмена новой неоплаченной заявки возвращает только зафиксированный этим контуром резерв, однократно. Повторный статус не вызывает письмо повторно. Повторное открытие отменённой заявки запрещено. При succeeded/pending/waiting_for_capture/review отмена требует сначала завершить сверку/возврат платежа. Автоматический возврат денег не добавлялся. Старые заявки без записи резерва не увеличивают склад при отмене.

Уведомления/платёж – после коммита. Их сбой не отменяет существование заявки. При аварии между коммитом и уведомлением повторная квитанция честно сообщает, что доставка не подтверждена. Автоматической очереди повторной доставки пока нет: офис проверяет сохранённые заявки. SMTP офиса теперь поддерживается через OFFICE_EMAIL; email+telegram проверяют оба результата. В тесте письма пришли в Mailpit офису и заявителю, реальные сообщения не отправлялись.

Откат интерфейса возможен по сохранённому исходному снимку. Откат складского кода требует остановить оформление, сохранить orders/club_checkout_commits/products и сначала разобрать действующие резервы. Нельзя просто удалить служебную таблицу: это потеряет знание о зарезервированных вещах и ключах повторов. Возврат к прежнему коду без этого небезопасен. Предпочтителен исправляющий релиз с сохранением добавочной таблицы. Перед production нужен пробный прогон на обезличенной копии актуальной схемы, проверка разрешений выделенного пользователя БД и резервная копия.

Подтверждения: stage4-transaction.log – пять тестов на реальном PostgreSQL: один запрос дважды, два клиента на последнюю единицу, rollback после первой позиции, двукратная отмена, запрет отмены оплаченного. stage4-flow.log – браузерная заявка ALU-2026-000002 и кабинет после reload; Mailpit содержит два соответствующих письма. Обычные unit-тесты используют fake-checkout исключительно для проверки HTTP-валидации; они не доказывают транзакционность.

Дополнительная проверка гонки оплаты: при включённом провайдере pending сохраняется вместе с заявкой до внешнего запроса. Администратор не может отменить резерв между сохранением заявки и получением payment_id. Неоднозначный сбой создания платежа требует сверки провайдера, а не автоматического освобождения резерва. Покрыто отдельным тестом настоящей PostgreSQL. Реальные деньги не использовались.

Оформление подписки сериализовано по выпускнику через PostgreSQL advisory lock. Два одновременных запроса в изолированном API вернули один номер; подписку активировало отдельное решение администратора. После истечения права ранее выданная подписанная аудиоссылка немедленно вернула 403.

Синхронизация ДПО не изменяет одноимённые ручные программы без HSE source_url, прекращает весь прогон при недоступном втором списке или пустом актуальном списке, сохраняет существующую цену/дату при отсутствии новых значений, оставляет новую программу без цены черновиком, включая повторный синк. Ручные модули и описание сохраняются. Эти ветви проверены изолированными тестами парсера/синхронизации; массовая синхронизация production не запускалась.
