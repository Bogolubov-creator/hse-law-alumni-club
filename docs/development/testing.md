# Проверка приложения и выпуска

Этот документ описывает сценарии, границы тестовых наборов и команды запуска.
Результаты конкретного коммита и незавершённые проверки записываются только в
[журнал состояния](../operations/project-state.md). Порядок установки, обновления и восстановления
находится в [runbook](../operations/deploy-runbook.md).

## Окружение

Команды выполняются из корня репозитория. Используются Node.js 24, pnpm 12.8.1 и
зависимости из `pnpm-lock.yaml`: Vitest 5.0.2, Vite 8.3.1 и Playwright 1.63.0.
Интеграционный сценарий запускает PostgreSQL 16.15 в одноразовом контейнере.
Точные версии и digest находятся в [Compose](../../docker-compose.yml),
[postgres.Dockerfile](../../deploy/postgres.Dockerfile) и [edge.Dockerfile](../../deploy/edge.Dockerfile).

Для тестов нужны синтетические аккаунты. Рабочий `runtime.env`, база участников,
платёжные ключи и внешние каналы уведомлений в тестовый процесс не передаются.
Тесты не запускаются на публичном сайте. Mailpit проверяет формирование и получение
письма локальным SMTP; доставку в реальный почтовый ящик он не подтверждает.

## Что проверяет каждый набор

| Набор | Настоящие компоненты | Подмены и ограничения | Точка входа |
|---|---|---|---|
| Общие правила | Денежные расчёты, скидки, номера, URL, правила баллов | Без HTTP и БД | `packages/shared/tests/*.test.ts` |
| API unit и HTTP | Обработчики Fastify, схемы Zod, guards, ответы через `inject` | Многие файлы подменяют слой данных, провайдеров и auth persistence; ядро Argon2 может оставаться настоящим | `backend/tests/unit/**/*.test.ts` |
| PostgreSQL integration | SQL-миграции, транзакции, блокировки, ограничения и откат | Чистая схема из настоящих SQL-миграций; внешние провайдеры выключены | `scripts/tests/test-integration.sh` |
| Bootstrap SQL | Чистая и legacy-схема, Argon2, транзакции, advisory lock | Только выделенный localhost PostgreSQL с правом создавать временные БД | `native-bootstrap.test.ts` |
| UI E2E | Браузер, DOM, маршруты, размеры экрана и состояния интерфейса | Многие сценарии используют `page.route` с фикстурами; успешный экран не доказывает запись в БД | Обычный `playwright.config.ts` |
| Live stack | Собранные web/API, PostgreSQL, Caddy, нативный bootstrap и Mailpit | Платежи, Telegram, push, Sentry и фоновые синхронизации выключены; локальный HTTP | `scripts/tests/test-live.sh` |
| Caddy Go | Исправленная сборка, CEL JSON privacy/matchers, govulncheck | Анализ достижимых вызовов vendor-исходников; внешний ACME отдельно | `edge.Dockerfile --target edge-check` |
| Edge TLS/HTTP | Финальные web/Caddy, localhost CA, reload, заголовки и лимиты | HTTP-фикстура API; собственные временные контейнеры/сети | `scripts/tests/test-edge.py` |
| Установщик Ubuntu | Зависимости, production-конфигурация, локальный TLS, PostgreSQL и вход администратора | Одноразовый Ubuntu runner, Mailpit; повтор сохраняет env и доступ | `scripts/tests/test-install.sh` |
| Эксплуатация Ubuntu | Compose, внешняя конфигурация, TLS, копия и изолированное восстановление | Требует отдельного запуска на целевой VM; unit-тесты скриптов его не заменяют | [Runbook](../operations/deploy-runbook.md) |

API-тесты могут использовать production-функцию расчёта переходов с хранилищем в
памяти. Это проверяет HTTP-контракт, но не атомарность SQL. Поэтому платёжный
путь дополнительно проверяется в настоящем PostgreSQL.

## Матрица пользовательских сценариев

В колонке live указано содержимое сценария, а не результат последнего запуска.
Часть действий в нём выполняется браузером, часть – прямым запросом к настоящему API.

| Сценарий | Автоматическая проверка | Live stack и оставшаяся граница |
|---|---|---|
| Регистрация и согласие | `auth.test.ts`: обязательные поля, согласие, honeypot, дубликат | Форма `/join`, письмо Mailpit, ссылка `/confirm` |
| Подтверждение почты | Назначение, подпись, срок ссылки, повтор, блокировка пользователя | Страница подтверждения и последующий вход; доставка внешним SMTP отдельно |
| Восстановление пароля | Одинаковый ответ для неизвестной почты, одноразовость, `token_version`, отсутствие SMTP | Форма `/forgot`, письмо, `/reset`, новый вход; старый JWT получает `401`, в том числе после рестарта |
| Выход выпускника | UI-сценарии кабинета и сессии | Проверяется удаление токена из браузера. Отдельного серверного отзыва alumni JWT при обычном выходе нет |
| Выход сотрудника | `admin-guard.test.ts`: отзыв `jti` | Старый admin JWT отвергается сразу и после рестарта API |
| Профиль и верификация | `me.test.ts`, `admin-guard.test.ts`: разрешённые поля и роли | Непроверенный выпускник получает `403` на изменение; администратор подтверждает выпуск; профиль сохраняется после reload и рестарта |
| Публичные страницы | UI-наборы `public`, `a11y`, `sections-v2`, `event-details` | Live создаёт курс и открывает каталог ДПО. Остальные поверхности проверяются отдельными UI-сценариями |
| Корзина и заявка | `cart.test.ts`, `orders.test.ts`, расчёты `shared` | Через браузер: курс → корзина → заявка → кабинет; API офиса меняет статус; данные остаются после рестарта |
| Идемпотентность и склад | `checkout.integration.test.ts`: параллельный повтор, последняя единица, откат, однократный возврат | Проверяется настоящей БД. Двойной клик в UI сам по себе эту гарантию не доказывает |
| Событие и баллы | `admin-events.test.ts`, `engine.test.ts`: права и повторное начисление | RSVP и две отметки посещения через API; в журнале одно начисление, участие сохраняется после рестарта |
| Подписка на подкасты | `podcasts.test.ts`, `podcast-sub-grant.test.ts` | Повтор заявки возвращает тот же номер; администратор выдаёт подписку; доступ остаётся после рестарта |
| Оплата | `payments.test.ts` и `payment-store.integration.test.ts`: владелец, IP webhook, ответ провайдера, сумма/валюта, повтор и откат | В live магазин выключен. Реальный платёж, отмена и доставка webhook требуют отдельного тестового магазина |
| Администратор и редактор | `admin-guard.test.ts`: текущая роль/status, демотирование, блокировка, недоступное хранилище | Вход обеих ролей; редактор видит контент, не может верифицировать участника или читать поддержку; SQL-проба проверяет права runtime без CMS |
| Аватар и поддержка | `avatars.test.ts`, `support.integration.test.ts`: тип/размер файла, собственник обращения, административные права | Не входят в основную live-цепочку; визуальная загрузка аватара и работа поддержки требуют своего прогона |
| Фоновые задачи | `jobs.test.ts`: флаги, часовой пояс, перекрытие запусков, остановка и ошибки | Live запускается с `JOBS_ENABLED=false`; реальное расписание проверяется отдельно |

Ссылки на наборы: [API](../../backend/src), [SQL-сценарии оплаты](../../backend/tests/integration/payment-store.integration.test.ts),
[live-сценарий](../../frontend/tests/e2e/live-stack.spec.ts), [браузерные сценарии](../../frontend/tests/e2e).
Сохранение ручных изменений и восстановление после частичного SQL-сбоя – разные
случаи. Bootstrap-набор внедряет ошибку при создании связи страницы и проверяет
откат всех ранних записей. Native auth-набор аналогично проверяет сбой после
обновления хеша и при создании анкеты.

## Установка и быстрые проверки

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm -r build
pnpm -r test
pnpm audit --prod --audit-level high
docker compose --env-file .env.example config --quiet
python3 scripts/tests/test-ops.py
```

`build` включает TypeScript всех пакетов и сборку web. Обычный `pnpm -r test`
пропускает интеграционные тесты, пока не заданы их флаги. Число пропущенных тестов
нужно сохранить в результате, а затем выполнить отдельный PostgreSQL-набор.
Исключения audit разобраны в [документе безопасности](security.md).

Для точечной проверки auth, платежей и задач:

```bash
pnpm --filter @club/api test tests/unit/modules/auth/routes.test.ts tests/unit/modules/auth/admin-guard.test.ts tests/unit/modules/checkout/payment-routes.test.ts tests/unit/jobs/jobs.test.ts
pnpm --filter @club/scripts test
```

Синтаксис shell проверяется отдельно:

```bash
for script in scripts/*.sh; do
  bash -n "$script" || exit 1
done
```

## Настоящий PostgreSQL

```bash
pnpm --filter @club/shared build
pnpm --filter @club/server-auth build
bash scripts/tests/test-integration.sh
```

Скрипт создаёт контейнер с уникальным именем, временной БД `alumni_staged` на tmpfs
и случайным loopback-портом, применяет все файлы `backend/migrations/*.sql`
в порядке имён, начиная с нативной основы. Отдельная упрощённая схема не применяется.
Затем запускает data adapter, native auth, checkout, payment-store, поддержку,
Telegram linking и социальные новости. `trap` удаляет только этот контейнер. Имя БД `alumni_staged` в этом
скрипте не означает подключение к архивному staged-стенду.

Платёжный SQL-тест намеренно вызывает ошибку второй записи: изменение подписки
должно откатиться вместе с заказом. Он также проверяет одновременные дубли,
параллельную выдачу подписки офисом, неверную сумму, валюту и позднюю оплату
закрытого заказа. Запуск с пропусками не считается проверкой этих гарантий.

Bootstrap-набор имеет отдельный opt-in: задайте `NATIVE_BOOTSTRAP_TEST_DATABASE_URL`
на выделенный локальный сервер с базой `club_native_test`, затем выполните
`pnpm --filter @club/scripts test`. Хелпер проверяет localhost и имя БД, создаёт
случайные временные базы и удаляет их после теста. Нужны права CREATE DATABASE;
рабочий URL не подходит. Без переменной SQL-кейсы пропускаются, unit остаются.

## Браузер с настоящими сервисами

```bash
pnpm --filter @club/web exec playwright install chromium
bash scripts/tests/test-live.sh
```

На Ubuntu для системных библиотек браузера используется
`pnpm --filter @club/web exec playwright install --with-deps chromium`.
Скрипт проверяет, что проект `club-ci-live`, его тома и порты `8180`, `8181`, `8182`
свободны. Он генерирует временные credentials, строит образы и выполняет:

1. Миграции, bootstrap, создание editor операторской CLI и SQL-пробу прав runtime.
2. Запись данных на desktop и mobile через настоящий стек.
3. Подготовку ручных изменений настроек, контента и паролей.
4. Два bootstrap с проверкой сохранения этих изменений.
5. Полную зашифрованную копию БД и uploads с возвратом API в healthy.
6. Рестарт PostgreSQL, API, web, Caddy и Mailpit без удаления томов.
7. Чтение сохранённых данных и проверку отозванных сессий на обоих размерах экрана.

Оба live-проекта используют Chromium; mobile – эмуляция iPhone 13, а не физическое
устройство и не Safari. Service worker здесь выключен. Выходной код становится
успешным только после всех фаз и удаления созданных ресурсов. Скриншоты находятся
в `frontend/test-results/live/`; токены и временные состояния не коммитятся.

Для локальных UI-наборов уже запущенного тестового сайта:

```bash
pnpm --filter @club/web exec playwright install chromium webkit
E2E_BASE_URL=http://localhost pnpm --filter @club/web e2e --project=desktop --project=mobile tests/e2e/public.spec.ts tests/e2e/auth-recovery.spec.ts tests/e2e/admin.spec.ts
pnpm --filter @club/web e2e:safari
```

На Ubuntu добавьте `--with-deps` к команде установки браузеров. Здесь mobile
использует WebKit, поэтому он нужен для обеих UI-команд. В отдельном live-наборе
mobile использует Chromium. Эти команды не поднимают сервер. Проверки PWA
выполняются отдельно в `pwa-runtime.spec.ts`.
Архивные `staged-*.spec.ts` исключены по умолчанию. Флаг `E2E_INCLUDE_STAGED=true`
допустим только после проверки их адресов, фикстур и разрешения на изменение
данных отдельного стенда. Их результаты не прибавляются к основному live-набору.

## Содержимое выпуска

После обычной сборки web выполните:

```bash
node scripts/checks/check-web-build.mjs frontend/dist
```

Проверка отклоняет исходники, sourcemap, тестовые и env-файлы, артефакты зеркала,
демо-токены и маркеры демоперехватчика. Она предназначена для обычной сборки;
`build:mirror` содержит демонстрационную логику по назначению.

После сборки финальных образов передайте реальные локальные теги или image ID:

```bash
bash scripts/checks/check-runtime-images.sh API_IMAGE BOOTSTRAP_IMAGE WEB_IMAGE
```

Скрипт запускает проверяющую команду без сети, с read-only файловой системой и
отключёнными capabilities. Он проверяет собственные каталоги приложения,
скомпилированные собственные модули, отсутствие перечисленных в скрипте dev/CMS-инструментов
и менеджеров пакетов в Node runtime, а также отсутствие исходников проекта,
его тестов и демоперехватчика в web. Сторонние npm-пакеты могут включать собственные
исходники, типы и map; проверка не запрещает эти файлы и сохраняет лицензии.
Собственная TypeScript-сборка исключает комментарии и sourcemap. JavaScript и типы
наших пакетов из финальных Node-образов дополнительно разбираются проверкой
`check-compiled-comments.mjs`; лицензии разрешены. Для этой проверки Node.js и
зависимости разработчика нужны на проверяющем компьютере, в рабочие образы они
не добавляются.
В CI для него используются `club-ci-live-api`, `club-ci-live-bootstrap` и
`club-ci-live-web`. Проверка содержимого не заменяет функциональные тесты и
сканирование известных уязвимостей.

Демо-сиды находятся в явном subpath `@club/shared/seeds`. Bootstrap загружает их
только при `APP_ENV=development` и `SEED_DEMO=true`; финальный API-образ не включает
`seeds.js` и `dpo-mirror-catalog.generated.js`. Пустой опубликованный контент
проверяется как пустой, без автоматической подстановки демонстрационных данных.

## Как фиксировать доказательство

Для каждого запуска сохраняются commit SHA, окружение, команда, код завершения,
количество passed/failed/skipped и оставшиеся ограничения. Для браузера дополнительно
указываются движок, размеры, наличие подмен API, ошибки страницы и проверка
сохранения данных. CI сверяется с точным SHA PR, а не с любым прежним зелёным запуском.

Исторические результаты Directus-стенда не подтверждают native-переход. После
замены auth, data, файлов, bootstrap или прав SQL повторяются относящиеся к ним
наборы и полный live. Конкретные counts, SHA, логи, проверки Ubuntu и scan digest
публикуются только в [project-state.md](../operations/project-state.md).

Перед выпуском дополнительно нужны проверка целевого HTTPS, восстановление
единого снимка БД и uploads, утверждённые внешние интеграции и контроль после
обновления по [runbook](../operations/deploy-runbook.md). Нагрузочный тест должен называть
измеренную нагрузку и ресурсы; количество функциональных тестов не измеряет ёмкость.
