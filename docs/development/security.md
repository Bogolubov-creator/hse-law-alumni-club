# Модель безопасности

Документ описывает действующие границы доверия, проверки кода и ограничения.
Он не является юридическим заключением, сертификацией или доказательством
безопасности публичного сервера. Результаты конкретной версии находятся в
[project-state.md](../operations/project-state.md), сценарии проверок – в [testing.md](testing.md).

## Активы и границы доверия

| Актив | Где хранится | Кто имеет технический доступ |
|---|---|---|
| Профиль, контакты, статусы выпуска и заявки | PostgreSQL; выдаются через API | API, администратор; отдельные списки доступны редактору через API |
| Пароли и сессии | Argon2 PHC-хеши в совместимой таблице пользователей, JWT клиента и записи отзыва в БД | Владелец сессии; серверные секреты подписания только у API |
| Баллы, скидки, резервы и подписки | Прикладные таблицы PostgreSQL | Серверные правила и уполномоченные сотрудники |
| Идентификатор и статус оплаты | Заказ в БД; состояние у ЮKassa | API и платёжный провайдер; реквизиты карты приложение не принимает |
| Файлы и аватары | Том `directus_uploads`, записи `directus_files` | API; опубликованные аватары доступны через специальный маршрут |
| Ключи и конфигурация | Внешний `/etc/club/runtime.env`; окружение контейнеров | Оператор сервера и процессы соответствующих сервисов |
| Резервная копия | `/var/backups/club`; offsite только при настройке | Оператор и явно подключённое хранилище |
| Аудит и технические журналы | `audit_log`, Docker/journald, служебные таблицы | Администратор/оператор; при включении Sentry появляется внешняя граница |

Браузер, поля формы, URL, файлы, роли из клиентского токена и тело webhook считаются
входными данными. Caddy принимает HTTP/HTTPS и передаёт запросы API. API обращается
к PostgreSQL под отдельной SQL-ролью и читает/пишет uploads через файловый модуль.
Схема соединений и портов приведена в [architecture.md](architecture.md).

Docker host и его socket находятся внутри привилегированной границы: оператор
Docker может читать окружение и тома. Отдельный контейнер не защищает данные от
скомпрометированного root хоста. Прикладной runtime не получает Docker socket.

## Роли и серверная авторизация

| Субъект | Разрешения API | Существенная граница |
|---|---|---|
| Гость | Опубликованный контент, регистрация, корзина и оформление заявки | Не получает `/me`, админку или оплату чужой заявки |
| Выпускник с заявкой | Собственный кабинет в пределах `verification_status` | Подтверждение почты и проверка выпуска – разные статусы |
| Проверенный выпускник | Собственный профиль, заявки, участие, доступная подписка | Суммы, скидки, принадлежность и право доступа проверяет API |
| `editor` | Контент, списки участников и заявок, изменение статуса заявки | Не получает CSV-выгрузку, изменение скидки/верификации, начисление баллов, выдачу подписки, обезличивание, текст поддержки |
| `admin` / `Administrator` | Полные операции панели | Требуется действующий пользователь и актуальная роль в PostgreSQL |
| `POINTS_SERVICE_TOKEN` | Необязательное внешнее начисление баллов | Не принимается вместо admin/alumni JWT |
| `club_api` | SQL-доступ серверных модулей | Не владелец БД; без UPDATE роли пользователя и чтения CMS-настроек |

Редактор панели видит отдельные персональные данные участников и заявок, но не
получает чувствительные выгрузки и изменения. Studio и сервисного аккаунта CMS
в новой архитектуре нет. Имена ролей `admin`, `Administrator`, `editor`, `alumni`
сопоставляются явно; статус verified не предоставляет прав сотрудника.

В [service.py](../../backend/club_api/modules/auth/service.py) `resolve_admin` проверяет HS256, назначение
сессии и отзыв `jti`, затем читает текущие status, роль, provider/TFA и поколение
служебной сессии из PostgreSQL. Блокировка, удаление и понижение роли действуют на
следующий запрос; ошибка хранилища закрывает доступ. `require_full_admin` отдельно
проверяет полную роль. Асинхронный guard всегда вызывается через `await`.

Alumni JWT ограничен сроком и сверяется с `token_version` профиля. Сброс пароля
увеличивает версию и отзывает прежние сессии. Обычный выход выпускника удаляет
токен из браузера; отдельного отзыва каждой такой сессии на сервере нет.
Admin logout сохраняет отзыв `jti` в БД и восстанавливает список при старте.

## Нативный auth, SQL-права и bootstrap

[passwords.py](../../backend/club_api/modules/auth/passwords.py) использует argon2-cffi 25.1.0 только
на сервере. При проверке читаются параметры сохранённого PHC-хеша; переход не
переписывает существующие хеши. Несовместимый хеш, внешний provider или TFA не
превращаются в обход проверки. Старые SSO/MFA-аккаунты сохраняются, но вход по одному
локальному паролю закрыт до отдельного решения о поддержке этих способов входа.

Регистрация атомарно создаёт пользователя строго alumni и его профиль, защищена
блокировкой нормализованного email. Публичные forgot/reset и подтверждение почты
проверяют действующую роль alumni и допустимый status. Reset повторно проверяет
эти условия и одним COMMIT меняет хеш, `token_version` и одноразовое состояние ссылки.
Одинаковый ответ forgot не раскрывает существование учётной записи офиса.

| Слой | Разрешение и ограничение |
|---|---|
| Общий [store.py](../../backend/club_api/db/store.py) | Таблицы/столбцы из allowlist, значения параметризованы; нет password/token/TFA, CMS metadata, произвольного SQL или изменения системных ролей |
| Специализированный auth | Узкие запросы хеша, provider, TFA, текущей роли; пароль не входит в возвращаемую публичную модель |
| SQL-роль `club_api` | CRUD бизнес-таблиц/файлов; чтение ролей; перечисленные поля пользователей; UPDATE email/password/name/status, без UPDATE role/token |
| Владелец БД | Миграции, bootstrap и операторское управление сотрудниками; его credentials не передаются API |
| `club_settings` | `site` с whitelist и полный приватный legacy-архив; у runtime нет доступа к этой таблице |

Источником SQL-прав служит [runtime-role.sql](../../backend/sql/runtime-role.sql).
Разрешения столбцов не заменяют разграничение строк: runtime обслуживает всех
участников, читает нужные auth-хеши и может обновлять разрешённые столбцы. Защиту
от изменения чужого пользователя и создания staff обеспечивает код API. Компрометация
самого API даёт более широкий доступ к данным, чем JWT отдельного участника.

Нативная миграция сохраняет UUID, внешние ключи и данные, создаёт только три
совместимые системные таблицы на новой установке. Обнаруженные дубликаты
`alumni.user_id` останавливают миграцию без удаления. Полные legacy-настройки
могут содержать ключи интеграций и остаются приватными даже после удаления CMS.

Bootstrap работает в транзакции с advisory lock и добавляет только отсутствующие
данные. Он сохраняет пароль, provider/TFA, роль, контент и настройки существующего
аккаунта; неожиданная роль или status начального администратора завершают запуск
ошибкой. Никакой пароль сервисного аккаунта из токена больше не создаётся.

Сотрудниками управляет [staff.py](../../scripts/club_ops/staff.py) от владельца
БД. Пароль передаётся через stdin или `STAFF_PASSWORD`, не через argv. Создание не
перезаписывает аккаунт; сброс требует ожидаемую роль, active, локальный provider и
отсутствие MFA. Хеш и поколение в `club_staff_sessions` меняются атомарно, поэтому
старые admin JWT перестают работать. Команда не повышает выпускника до сотрудника.

## Основные угрозы и защитные границы

| Сценарий | Защита | Остаточная граница |
|---|---|---|
| Подмена цены, роли или чужого ID браузером | Серверный расчёт, схема запроса, проверка владельца и текущих прав | Ошибка нового маршрута требует отрицательного теста |
| SQL-injection через фильтр/идентификатор | Закрытый DSL, allowlist таблиц/полей и SQL-параметры | Внутренний слой не принимает команды напрямую из HTTP |
| Кража JWT через XSS | CSP, безопасный вывод, срок, отзыв/поколение | localStorage доступен скрипту того же origin |
| Поддельная/повторная оплата | Проверка API провайдера, суммы и ID, SQL-блокировки | Тестовый провайдер не доказывает настройку рабочего магазина |
| Загрузка активного файла или traversal | MIME/сигнатура, лимиты, собственное имя, проверка пути, отдельная выдача | Проверка сигнатуры не является антивирусом |
| Потеря хоста или компрометация root | Закрытые конфиги, согласованная зашифрованная копия, отдельный offsite | Локальная копия и Docker-изоляция не защищают от владельца хоста |
| Компрометация API | SQL-роль без полномочий владельца, запрет metadata/role update | Runtime обслуживает данные всех участников; PostgreSQL RLS не применяется |

## Браузер, CSRF, CORS и XSS

Сессии API передаются в `Authorization: Bearer`, а не автоматически прикрепляемой
cookie. Это уменьшает поверхность классического CSRF. API CORS допускает
настроенные origins и Telegram; запрос без Origin допускается. CORS не заменяет
аутентификацию и не запрещает запросы из произвольного HTTP-клиента.

Токены находятся в `localStorage`, поэтому XSS в собственном origin может их
прочитать. Для web Caddy задаёт CSP с `script-src 'self' https://telegram.org`,
ограничивает frame-источники RuTube и `frame-ancestors` Telegram/собственным origin.
`style-src` допускает inline-стили. API использует отдельную строгую CSP через
Helmet. Эти политики уменьшают риск, но не заменяют проверку вывода пользовательского
контента и ссылок.

Персональные, административные и платёжные ответы получают `Cache-Control: no-store`.
[Service worker](../../frontend/public/sw.js) не кэширует API и HTML кабинета;
кэш статических файлов ограничен scope. HTTPS и физическое устройство проверяются
отдельно от браузерной эмуляции.

## Транспорт и секреты

Рабочий API требует `APP_ENV=production` и `SEED_DEMO=false`; небезопасные значения
проверяет [config.py](../../backend/club_api/core/config.py). Публичный HTTPS завершает Caddy.
Внутри Docker bridge Caddy → API использует HTTP, подключение к PostgreSQL
остаётся внутренним. Это доверие к одному host и его сети, а не сквозное TLS
между каждым контейнером.

Порт API не публикуется на host. `trustDockerProxy` доверяет только первому хопу
из частных IPv4-сетей Docker; добавление прямого порта или нового proxy требует
пересмотра проверки IP, rate limit и webhook. HSTS имеет смысл только после
работающего HTTPS. Локальный HTTP live-набор не проверяет HSTS, DNS или ACME.

Runtime env хранится вне checkout с правами `0600`, каталог – `0700`. Пароли,
токены, приватные ключи, дампы и uploads не включаются в git. `VITE_*` попадает
в браузерную сборку и не подходит для секретов. При ротации проверяются новый
ключ, отказ старого и связанные сессии; существующий bootstrap не является
универсальной командой ротации. Поля и стадии конфигурации описаны в
[configuration.md](configuration.md).

## Загрузки, внешние URL и провайдеры

Аватар ограничен одним файлом JPEG/PNG/WebP до 3 MiB. MIME, сигнатура и настоящее
декодирование проверяются до SQL-записи. [service.py](../../backend/club_api/modules/media/service.py)
использует sharp 0.35.5: ответ PNG 256×256 cover, поворот по EXIF, удаление EXIF/ICC/XMP.
Исходный файл не переписывается. Для чтения прежнего аватара предел оригинала –
10 MiB; декодер ограничен 16 MP и тремя секундами. В процессе допускаются два
преобразования и восемь ожидающих; одинаковые запросы объединяются, кэш ограничен
64 записями, 16 MiB и пятью минутами. Перегрузка получает временный отказ.

Медиараздел офиса принимает изображения JPEG/PNG/WebP до 10 MiB и аудио
MP3/WAV/OGG/M4A до 128 MiB без преобразования. Legacy GIF/AVIF читаются, но новая
загрузка этих форматов не разрешена. SVG/HTML не принимаются. Проверка сигнатуры
аудио и офисного изображения не является антивирусом или полным декодированием.
UUID и bytes существующих uploads сохраняются.

Публичный `/api/media/:id` отдаёт изображения только со ссылкой из опубликованного
контента. Аватары обслуживаются отдельным `/api/avatars/:id`; аудио не
становится общедоступным через legacy `/assets`: оно выдаётся маршрутом подкастов
после проверки права и подписи. Поддерживаются Range/206; закрытое аудио получает
private-кэш. Удаление используемого файла блокируется, включая ссылки из JSON/текста.
Модуль проверяет имя файла и запрещает выход из каталога через traversal/symlink.
Импорт произвольного URL в upload не выполняется.

Новостной импорт использует фиксированные источники, нормализацию разрешённых URL,
запрет редиректов, таймаут 15 секунд и предел ответа 2 MB. Каталог ДПО использует
URL оператора из окружения; его fetch не имеет тех же ограничений на redirect,
время и размер. Поэтому нельзя заявлять общую SSRF-защиту всех исходящих запросов.
Изменение источника требует проверки URL и сети назначения. Произвольный URL
пользователя не должен превращаться в серверный fetch.

Webhook ЮKassa проверяет адрес отправителя и запрашивает платёж напрямую у
провайдера. Успех требует совпадения связанного payment ID, суммы в копейках,
валюты RUB и признака `paid`. Заказ и продление подписки меняются в одной
SQL-транзакции с блокировками. Повторы не должны начислять ещё один срок, а несовпадение
или поздняя оплата закрытого заказа переводится на сверку. Проверка pending/canceled,
задержанного ответа и частичного сбоя включена в [матрицу тестов](testing.md).

Telegram webhook использует свой секрет и отдельную проверку входных данных;
polling не отключает существующий webhook. При выключенных ключах интеграция
не считается подключённой. В текущей локальной проверке внешняя рассылка,
реальная оплата, Telegram и push не выполняются.

## Журналы, аудит и фоновые задачи

Стандартный журнал HTTP сохраняет путь без query string, метод и адрес клиента;
Authorization, cookie и типовые поля секретов маскируются. Прямые сообщения ошибок
и подключаемые библиотеки всё равно требуют проверки: redaction нескольких полей
не гарантирует очистку произвольной строки. Аудит может содержать email, IP и
идентификаторы действий и сам относится к чувствительным данным.

`audit()` пишет событие асинхронно. Сбой записи не отменяет бизнес-операцию;
ошибка остаётся в журнале. Это не транзакционный, неизменяемый или криптографически
подписанный журнал: runtime SQL-роль имеет права записи и удаления этой таблицы.
Важные расследования должны учитывать эту границу полноты и сохранности.

Sentry включается только при DSN и отправляет фиксированные коды ошибок.
`before_send` удаляет все остальные поля: запросы, пользователя, исключения,
breadcrumbs, SQL и stack locals. Автоматические интеграции отключены. Доставка
внешнему сервису в локальных тестах не выполняется.

Задачи `jobs/runner.py` исполняются в одном API, используют `Europe/Moscow`, пропускают
перекрывающийся запуск той же задачи и имеют ограниченное ожидание остановки.
Часть rate limit и блокировок хранится в памяти. Добавление второй реплики требует
общего состояния и распределённой координации. `JOBS_ENABLED=false` выключает
планировщик и стартовые операции для изолированных проверок.

## Проверка зависимостей и секретов

`pip-audit` проверяет runtime и инструменты разработки всех Python-пакетов по
закреплённым lockfile. Trivy отдельно проверяет итоговые образы; аудит библиотек
не заменяет проверку runtime и прав доступа.

[Dependabot](../../.github/dependabot.yml) каждый рабочий день проверяет Python
через `uv`, включая транзитивные зависимости в трёх lock-файлах, а также GitHub
Actions, Docker и корневые Go-модули Caddy. Python-обновления группируются в один PR,
чтобы проверять общий граф зависимостей. Новые версии проходят все задания CI
до слияния; выпуск с несовместимыми требованиями сначала требует адаптации.
Связанные версии, например `pydantic-core` и `pyee`, выбирает родительский пакет.
Нельзя принудительно обходить его ограничения ради номера последнего выпуска.

Ручная проверка и обновление Python lock-файлов:

```bash
uv lock --directory backend --upgrade
uv lock --directory frontend --upgrade
uv lock --directory scripts --upgrade
```

После обновления перечитайте diff и выполните проверки зависимостей из
[AGENTS.md](../../AGENTS.md). Версии Django в API и web обновляются вместе.
Порядок обновления Caddy описан в
[решении о сборке](../decisions/caddy-dependencies.md).

Ежедневный монитор в Codex проверяет весь Go-граф, включая вложенные модули.
Dependabot ошибочно выбирает версию `golang.org/x/crypto` для отдельного модуля
`golang.org/x/crypto/x509roots/fallback`; обновления транзитивных Go-зависимостей
готовятся через штатную сборку Caddy и проверяются CI.

HTML-шаблоны Jinja2 используют экранирование; собственные браузерные модули
создают текстовые узлы. React Router и серверные RSC actions в проекте отсутствуют.
Комментарии собственного кода проверяются отдельной командой; обязательные
лицензии стороннего кода сохраняются.

Gitleaks проверяет и текущие файлы, и историю разными запусками. При разборе
330 коммитов найдено 6 совпадений: три фиксированных синтетических значения
`backend/tests/unit/config/env.test.ts`, каждое в двух коммитах. Это классификация конкретных
совпадений, а не доказательство отсутствия иных секретов.

[.gitleaks.toml](../../.gitleaks.toml) включает стандартные правила.
Исключения прежнего TypeScript-теста убраны. Единственное исключение требует
точного пути `legacy-auth.json` и полного фиксированного JWT с синтетическим
секретом: тест совместимости проверяет его подпись. Новые совпадения
разбираются отдельно; рабочий секрет отзывают, а не добавляют в allowlist.

В [CI](../../.github/workflows/ci.yml) Gitleaks 8.30.1 закреплён digest и запускается
в режиме `dir` с read-only mount, без сети и с `--redact`. Такой job проверяет
файлы checkout; полная история требует отдельного `git`-сканирования полного клона.
Trivy проверяет образы отдельно от pip-audit. После удаления Directus необходимо
проверять именно итоговые native-образы API, PostgreSQL, web/Caddy и используемые
инструменты. Caddy и gosu пересобираются с закреплённым Go и модулями; успешный скан
старого digest не переносится на новый. Сопоставление advisory с runtime-путём,
build-инструментом или неиспользуемым пакетом выполняется явно. Нулевой счётчик
сканера не доказывает отсутствие ошибок ядра, как показало [исследование d9](../decisions/cms-options.md).
Подробные результаты и проверенные digest фиксируются только в журнале состояния.

## Остаточные риски и условия выпуска

| Граница | Что нужно для закрытия |
|---|---|
| Замена CMS собственными модулями | Пройти native auth/data/media, legacy-перенос, полный live и Ubuntu restore; права и сохранение данных проверять в каждом контуре |
| Старые SSO/MFA и legacy-файлы | Не выключать факторы входа; сверить UUID, bytes, ссылки и отображение реальных разрешённых форматов на изолированной копии |
| XSS и JWT в браузере | Сохранять CSP и безопасный вывод; пересматривать хранение сессий при изменении модели клиента |
| Один API и память процесса | Не масштабировать реплики без общего rate limit, блокировок и согласованного отзыва |
| Копия на том же host | Проверить полный restore; подключить и прочитать offsite, если требуется пережить потерю сервера |
| Аудит и внешняя телеметрия | Уточнить доступ, сроки хранения и полноту записи; отдельно разрешить внешнюю передачу |
| Образы и зависимости | Дождаться конкретного сканирования образов, разобрать достижимость находок и повторить при обновлении |
| Публичный сервер и интеграции | Проверить согласованный домен/TLS, SMTP, платёжный магазин и каждый включённый внешний канал |

При инциденте оператор ограничивает затронутую интеграцию, сохраняет доступные
журналы без публикации персональных данных, отзывает скомпрометированные credentials
и проверяет восстановление. Развёртывание и возврат к рабочей версии выполняются
по [runbook](../operations/deploy-runbook.md); произвольный сброс БД или `git reset --hard`
не используется как процедура реагирования.
